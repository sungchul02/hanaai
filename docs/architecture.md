# AI 키오스크 CMS 콘텐츠 추천 시스템 — 설계

> 키오스크 사용자 질문 데이터를 AI가 주기적으로 분석하여 반복적으로 발생하는 유용한 질문을
> 찾고, 새로운 FAQ 및 안내 메뉴를 자동으로 제안해 관리자가 CMS에 손쉽게 반영할 수 있도록
> 하는 시스템.

- 근거 문서: `2안_AI_키오스크_CMS_프로젝트_이해자료.pdf`
- 스택: Python 3.11+ / FastAPI / PostgreSQL 16 / SQLAlchemy 2.x + Alembic / Claude CLI

---

## 0. 전체 흐름

문서의 7단계를 그대로 구현한다.

```
 ① 사용자 ─질문─► ② question_log
                        │
                        ▼
                  ③ 분석 (규칙)          분류 · 묶기 · 빈도 · 커버리지
                        │  주제 수십 개
                        ▼
                  ④ 분석 (LLM)           메뉴명 + 안내 문구 초안
                        │  content_proposal
                        ▼
                  ⑤ 관리자 CMS           [추가하기] [수정] [무시]
                        │
                        ▼
                  ⑥⑦ cms_menu 반영 ──► 키오스크가 그 질문에 답하기 시작
```

**핵심 설계 원칙 세 가지**

1. **AI는 추천만, 반영은 사람이.** 승인 없이는 아무것도 키오스크에 나가지 않는다.
   승인 한 번이면 그대로 고객에게 보이는 문장이라, 자동 반영은 위험 대비 이득이 없다.

2. **LLM은 판단만, 세는 건 규칙이 한다.** 질문 수천 건을 모델에 넣지 않는다.
   "자주 묻는다"는 빈도 자체를 LLM이 셀 수도 없다. 규칙이 주제 수십 개로 줄이고,
   LLM은 그중 무엇이 메뉴가 될 만한지 판단하고 문구를 쓴다.

3. **답하지 못한 기록이 원재료다.** 키오스크가 모르는 질문에 생성형으로 답해버리면
   당장은 그럴듯하지만 "어떤 주제에 콘텐츠가 없는지"를 영원히 알 수 없게 된다.
   그래서 매칭 실패는 감추지 않고 그대로 남긴다.

## 1. 데이터

| 테이블 | 역할 |
|---|---|
| `customer` / `site` / `kiosk` | 플릿. 고객사 단위로 CMS가 갈린다 |
| `cms_menu` | 지금 답할 수 있는 안내 콘텐츠. 분석의 '이미 있는 것' 기준 |
| `question_log` | **원재료.** 질문 원문, 정규화 문자열, 나간 답, 매칭된 메뉴, 판정 |
| `question_cluster` / `_member` | 묶인 주제와 소속 질문 |
| `content_proposal` | AI 추천 콘텐츠. 승인 게이트가 걸리는 곳 |
| `analysis_run` | 분석 실행 이력. 재현과 비용 추적 |

**`question_log.answer_source`가 이 시스템의 신호다.** 세 단계로 나뉜다.

| 값 | 뜻 | 분석에서 |
|---|---|---|
| `cms_menu` | 질문이 묻는 것을 메뉴가 충분히 설명했다 | 답한 것으로 센다 |
| `low_confidence` | 스치듯 걸렸다. 답은 보여주되 확신이 낮다 | **공백으로 센다** |
| `fallback` | 아무것도 못 찾았다 | 공백으로 센다 |

가운데 단계가 있어야 하는 이유: "주차장 자리 얼마나 남았어" 가 '주차장' 한 단어 때문에
주차 안내(위치·요금)로 답해졌고, 그게 응답 완료로 기록되어 '실시간 주차 대수' 라는
진짜 공백이 묻혔다. 확신이 낮으면 낮다고 남겨야 분석이 그걸 찾아낸다.

**`cms_menu.origin`으로 AI가 만든 메뉴를 표시한다.** 나중에 "AI 추천이 실제로 쓸모
있었나"를 재려면 사람이 만든 것과 구분되어 있어야 한다.

규모가 커지면 `question_log`를 `asked_at` 월 파티션으로 바꾼다. 지금은 인덱스로 충분하다.

## 2. 분석 — 1단계 (규칙)

`agents/analyst/` · LLM을 쓰지 않는다.

**① 거르기** — 욕설과 너무 짧은 입력만 규칙으로 판정한다.
'안내와 무관한가'는 여기서 판단하지 않는다. 질문 하나만 보고는 알기 어렵고,
묶어놓고 보면 훨씬 분명해진다. 그 판단은 클러스터 단위로 LLM이 한다.

**② 묶기** — 형태소 분석기나 임베딩을 쓰지 않는다. 짧은 구어체 질문에서 형태소 분석기는
자주 틀리고, 임베딩은 학생 프로젝트 환경에 무겁다. 대신:

- 말투(`위치 알려주세요`, `어디예요`)를 떼어내고 **내용어만** 남긴다
- 서술어로 끝나는 낱말(`있어요`, `주세요`)을 버린다
- 남은 낱말끼리 글자 단위로 견준다 (`주차`↔`주차장`은 붙고 `화장실`↔`주차장`은 떨어진다)

정확도가 더 필요해지면 `textutil.similarity()` 하나만 임베딩 기반으로 갈아끼우면 된다.
나머지 코드는 이 함수만 본다.

**③ 빈도** — 묶음 크기와 미응답 수를 센다.

**④ 커버리지** — 이미 답할 수 있는 메뉴가 있는지 본다.
1순위는 **실제로 답이 나간 기록**이다(`matched_menu_id`). 추측할 이유가 없다.
키워드 유사도는 아직 답한 적 없는 경우에만 쓴다.

## 3. 분석 — 2단계 (LLM)

`agents/analyst/generator.py` · 백엔드 교체 지점이 이 파일 하나다.

| 백엔드 | 용도 |
|---|---|
| `claude-cli` (기본) | 로그인된 Claude CLI. API 키 불필요 |
| `claude-api` | `ANTHROPIC_API_KEY`. 기업 배포용 |
| `passthrough` | LLM 없이 규칙 기반. 테스트·오프라인 |

**출력 계약(`agents/contracts/proposal.py`)을 통과하지 못한 응답은 저장하지 않는다.**
승인 한 번이면 그대로 나가는 내용이라 형태가 헐거우면 관리자가 매번 손봐야 하고,
그러면 시스템의 존재 이유가 없어진다. 검증 실패는 버리되 이유를 `analysis_run.error`에 남긴다.

**프롬프트에서 가장 중요한 지시는 "모르는 사실을 지어내지 마라"** 이다.
위치나 요금을 질문에서 알 수 없으면 `(확인 후 입력 필요)`를 넣어 관리자가 채우게 한다.
틀린 안내가 나가는 것이 최악이다.

### CLI 백엔드에서 반드시 지킬 것

셋 다 실제로 당한 뒤에 넣었다. 빠지면 오류가 아니라 **조용히 이상하게** 동작한다.

1. **`.cmd` 셰임이 아니라 네이티브 실행 파일**을 쓴다. Windows npm 셰임은 cmd.exe를
   거치면서 개행이 든 `--system-prompt` 인자를 통째로 날린다.
2. **`--exclude-dynamic-system-prompt-sections`** 를 준다. 없으면 Claude Code의
   에이전트 프레이밍이 덧붙어 모델이 "스키마 파일을 찾아보겠다"며 산문으로 답한다.
3. **전체 JSON Schema를 붙이지 않는다.** 붙였더니 오히려 자기 형식으로 이탈했다.
   계약 모델로 만든 유효한 예시 하나가 훨씬 강하다.

## 4. 화면

| 화면 | 위치 | 내용 |
|---|---|---|
| A. 가상 키오스크 | `:8001/` | 질문 입력 → 답변. 답변 출처(응답/답변불가)를 그대로 보여준다 |
| B. 관리자 CMS | `:8000/` | 요약 카드 · 추천 콘텐츠(승인/수정/무시) · 주제 · 질문 · 메뉴 |

빌드 도구도 프레임워크도 쓰지 않는다. 각각 단일 HTML이 JSON API를 직접 호출한다.
지금 필요한 것은 '보이는 것'이지 SPA가 아니다.

문서대로 분석은 **버튼 방식**이다(`POST /v1/analysis/run`). cron으로 돌릴 때도 같은
함수를 부르면 된다.

## 5. 우선순위

문서 5장을 그대로 따른다.

| 우선 구현할 것 | 상태 | 처음부터 필수는 아닌 것 |
|---|---|---|
| 질문/답변 로그 DB 저장 | 완료 | 실제 키오스크 기기 제작 |
| AI 질문 분류 | 규칙(욕설·길이) + 주제 단위 LLM 판단 | 실제 카메라 연동 |
| 비슷한 질문 그룹화 | 완료 | 실제 마이크/음성인식 연동 |
| 빈도 높은 주제 분석 | 완료 | 완성도 높은 TTS |
| AI FAQ/메뉴 생성 | 완료 (Claude CLI) | 복잡한 실시간 배포 |
| 관리자 CMS 승인/수정 | 완료 | 완전 자동 업데이트 |

## 6. 알려진 한계

**동의어를 못 묶는다.** "차 세울 데 있나요?"와 "주차장 어디예요?"는 글자가 겹치지 않아
따로 묶인다. 다만 두 묶음이 모두 LLM에 전달되고 LLM이 하나의 제안으로 합치므로
실사용에는 문제가 덜하다. 임베딩을 넣으면 1단계에서 해결된다.

**"기존 메뉴에 키워드만 추가하면 되는 경우"를 구분하지 못한다.**
"토요일에도 하나요?"는 운영시간 메뉴가 있는데도 매칭이 안 돼 미응답이 됐고,
AI는 새 메뉴를 제안했다. 콘텐츠가 없는 게 아니라 **키워드가 없는 것**이라
올바른 조치는 기존 메뉴에 키워드를 더하는 것이다. LLM에 기존 메뉴 목록을 함께 주고
'키워드 추가' 유형의 제안도 낼 수 있게 하는 것이 다음 개선점이다.

**질문 판정이 2단계로 나뉘어 있다.** 규칙은 욕설·길이만 보고 나머지는 `useful`로 둔다.
잡담 주제는 LLM이 제안하지 않는 것으로 걸러지지만, 질문 단위 판정으로 되돌아오지는 않는다.

**어휘가 겹치지 않으면 못 맞춘다.** "차 어디에 대면 돼요?" 는 주차 안내와 글자가 안 겹쳐서
답하지 못한다. 관리자가 키워드를 더하거나, 임베딩을 넣어야 해결된다.
한 글자 키워드('차')는 '자동차' '기차' 어디에나 걸려서 일부러 무시한다.

**인증이 없다.** 관리자 API에 누구나 접근할 수 있고, 고객사 간 격리도 질의 파라미터일 뿐이다.

## 7. 열린 질문

| 항목 | 필요한 결정 |
|---|---|
| 실제 질문 로그 | 현행 키오스크가 남기는 로그 포맷·샘플. 지금 시뮬레이터는 추정이다 |
| CMS 연동 | 사내 CMS가 따로 있는지, 있다면 `cms_menu`를 대체할지 연동할지 |
| 음성 입력 | STT 연동 여부. `input_mode` 컬럼은 이미 있다 |
| 운영자 인증 | OIDC 연동 대상 |

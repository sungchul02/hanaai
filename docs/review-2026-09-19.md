# 첫날 시나리오 관리자 검토 — 2026-09-19

천안시청 키오스크 설치 첫날(질문 103건)을 관리자 입장에서 처음부터 끝까지 돌려보고
기록한 것이다. 숫자는 전부 실제 실행 결과다.

```
질문 103건 → 주제 58개 → [규칙] 53개 제외 → [LLM] 5개 판단 → 전부 통과
           → 근거 확보 4 · 근거 없음 1 → 초안 14건
```

## 고친 것

### F1. 정리 규칙이 수정 루프에 지워졌다 (심각)

초안 14건 중 **11건**에 옆 메뉴가 다루는 내용이 `(확인 후 입력 필요)` 로 남아 있었다.

```
[주차 요금]      ... 주차비 카드 결제 가능 여부와 정산기 위치는 (확인 후 입력 필요).
                     ^ '주차 요금 결제 방법' 메뉴가 바로 옆에 있다
[주차장 운영시간] ... 주차 요금, 무료 주차 시간, 1일 최대 요금은 (확인 후 입력 필요).
                     ^ '주차 요금' 메뉴가 바로 옆에 있다
```

`placeholder.clean_body` 는 멀쩡했다. **호출 순서가 틀렸다.**

```
전:  생성 → 정리 → 검증 → 수정(본문 다시 씀) → 저장
                          ^ 수정이 정리를 되돌린다
후:  생성 → 검증 → 수정 → 정리 → 저장
```

`REVISE_PROMPT` 가 "질문에서 알 수 없는 것은 (확인 후 입력 필요) 로 남겨라" 라고
명시적으로 시키기까지 한다. 정리를 앞에 두면 반드시 되돌아온다.

고친 뒤 16문장과 키워드 19개가 정리됐고, 첫날 질문 12개 중 11개가 정확한 메뉴로 갔다.

### F2. 부서 위치 질문 13건이 통째로 사라진다 — 해결

부서명이 서로 낱말을 하나도 공유하지 않아 전부 1건짜리로 흩어졌다.
한국 관공서 부서명은 접미사 `과` 가 공통이므로, 3글자 이상이고 둘 다 `과` 로 끝나면
같은 부류로 보고 0.5 를 준다(`textutil.ORG_KINSHIP`).

`실` 은 넣지 않았다. 화장실 · 민원실 · 수유실이 전부 걸려 지금 제대로 갈린 주제가 뭉친다.
`관` 도 넣지 않았다 — 감사관(부서)과 도서관(시설)이 섞인다.

결과: 주제 58 → 51개, AI 판단 5 → 6개. `부서 안내` 8건이 주제로 올라왔다.

### F2-1. 그 수정이 더 나쁜 버그를 만들었다 — 해결

고치고 나서 확인해보니 **자신 있게 틀린 답**이 나왔다.

```
세정과 몇 층이에요?  → [안내 완료] 1층 부서 안내     세정과는 6층이다
축산과 몇 층이에요?  → [안내 완료] 1층 부서 안내     축산과는 5층이다
                        11건 중 8건이 오답
```

원인이 둘이었다.

1. `ORG_KINSHIP` 을 답변 매칭에서도 썼다. 세정과가 아무 `-과` 와도 0.5 로 걸렸다.
   묶을 때는 "부서 위치를 묻는 같은 질문" 이라는 뜻이지만, 답할 때는 세정과가 곧 세정과여야 한다.
   → `kinship` 을 기본 끔으로 두고 `cluster.py` 에서만 켠다.

2. **수정 루프가 초안을 망가뜨렸다.** 부서 8건을 층별 메뉴 7개로 쪼갰는데,
   각 메뉴가 주제 전체 8건을 혼자 감당하는 것으로 검증했다.
   '1층 부서 안내' 가 "세정과 몇 층이에요?" 를 못 잡는다고 미스로 잡혔고,
   수정 요청을 받은 모델이 지시대로 **세정과를 1층 키워드에 넣었다.**
   모든 층 메뉴에 모든 부서명이 들어가 전부 1.00 동점이 됐다.
   → 검증할 때 **형제 초안을 나란히 놓는다.** 형제가 잡는 질문은 미스가 아니다.
     운영에서도 형제와 나란히 놓이기 때문이다.

이 수정으로 **검증률의 뜻도 바로잡혔다.** 전에는 `주차장 운영시간 · 검증 81%` 처럼
개별 메뉴에 주제 전체 커버리지가 표시돼, 관리자가 "19% 를 못 잡는 나쁜 초안" 으로 읽었다.
이제는 형제와 함께 잰 값이라 "이 주제를 우리 메뉴들이 합쳐서 얼마나 덮는가" 를 뜻한다.

**교훈**: 묶기에 좋은 규칙이 답변에도 좋은 것은 아니다. 두 경로는 목적이 반대다 —
묶기는 비슷한 것을 모으고, 답변은 정확히 하나를 고른다.

## 남은 오류

### F3. 의도 분류가 너무 거칠다

`민원실 업무시간` 과 `민원실 휴무일` 이 둘 다 `시간` 의도로 잡힌다. 그래서

- "민원실 토요일에 하나요?" 가 **업무시간** 메뉴로 갔다. 그 본문에는 토요일 얘기가 없다.
- `민원실 업무시간` 키워드에 `민원실 토요일`, `민원실 주말`, `민원실 휴무` 가 남았다.
  정리 규칙이 둘의 의도가 같아서 구분하지 못한다.

**고칠 방향**: `시간` 을 `운영시간` 과 `휴무일` 로 가른다. 마커도 나눠 붙인다.
`요금` 도 `금액` 과 `결제수단` 으로 갈릴 여지가 있다.

### F4. 한 문장에 항목을 몰아넣으면 어떤 규칙으로도 못 가른다

```
"주차장 입구 위치와 들어가는 경로, 지하 주차장 유무, 전체 주차 대수,
 남은 자리 확인 방법, 야간 운영 여부는 (확인 후 입력 필요)."
   → 의도 {위치, 규모, 시간, 방법} 이 한 문장에 섞였다
```

지금은 통째로 지워지지만, 그중 하나만 진짜 빈칸이면 그것까지 잃는다.

**고칠 방향**: 프롬프트에 "빈칸은 항목당 한 문장으로 쓴다" 를 넣는다.
프롬프트로 안 되면 문장을 쉼표로 쪼개 항목별로 판정한다.

### F5. 쪼개기가 과하다

주제 5개에서 메뉴 14개가 나왔다. 질문 4건짜리 주제(무인발급기)에서 메뉴가 4개다.

```
무인발급기 4건 → 설치 위치 / 운영시간 / 24시간 운영 현황 / 발급 가능 서류
```

관리자가 4건을 한 번에 검토·승인해야 하고, CMS 목록도 그만큼 길어진다.

**고칠 방향**: 주제의 질문 수에 따라 쪼갤 상한을 둔다.
질문 4건이면 메뉴 2개까지 같은 식으로. 프롬프트에 숫자를 준다.

### F7. 잡음이 LLM 판단까지 가지 못한다

첫날 잡음 13건(잡담·욕설·개인 민원 조회)이 전부 1~2건짜리라 표본 부족으로 걸러졌다.
`triage_dropped = 0` 이다.

결과는 맞다 — 안내문이 안 만들어졌다. 하지만 **"AI 가 걸러냈다" 는 기록이 남지 않는다.**
`과태료 조회` 같은 것은 규칙으로 못 거르는 대표 사례인데, 하루치로는 그 장면이 안 나온다.

**고칠 방향**: 쌓인 날이 늘면 저절로 해결된다. 시연용으로는
잡음 클러스터도 표본 기준을 낮춰 LLM 에 보내는 선택지를 두는 것이 좋다.

## 있으면 좋겠는 것

### I1. 같은 주제를 여러 날에 걸쳐 누적해서 본다

지금은 분석할 때마다 그날의 클러스터를 새로 만든다. "주차 질문이 사흘째 늘고 있다" 를
볼 수 없다. 주제에 안정된 식별자를 주고 날짜별 추이를 쌓으면
관리자가 우선순위를 훨씬 쉽게 정한다.

### I2. 초안을 승인하기 전에 키오스크에서 미리 본다

지금은 `[미리보기]` 가 "이 메뉴가 어떤 질문을 새로 잡는지" 만 보여준다.
**시민이 실제로 보게 될 화면**을 그대로 보여주면 문장 길이와 말투를 판단하기 쉽다.
키오스크 화면은 이미 있으니 그 렌더링을 재사용하면 된다.

### I3. 문서 보강을 화면에서 끝낸다

지금은 `db/seeds/cheonan_documents.py` 를 고치고 `seed.py` 를 다시 돌려야 한다.
관리자가 터미널을 쓸 수 없다. 화면에서 문서 조각을 추가·수정할 수 있어야 한다.
`source_document` / `document_chunk` 는 이미 있으므로 쓰기 API 만 더하면 된다.

### I4. 답을 못 한 질문을 관리자에게 바로 보여준다

`answer_source = fallback` 인 질문이 곧 공백이다. 지금은 [질문] 탭에서
`답하지 못한 것만` 을 체크해야 보인다. 홈에서 "오늘 답 못 한 질문 N건" 을
바로 보여주면 분류를 돌릴 시점을 알 수 있다.

### I5. 분석을 자동으로 돌린다

지금은 관리자가 눌러야 한다. 문서(2페이지)에도 "처음에는 버튼으로 충분" 이라고 되어 있다.
운영에 들어가면 밤에 한 번 1단계까지만 자동으로 돌려두고,
아침에 관리자가 중간 보고부터 보는 것이 자연스럽다. 2단계는 사람이 고른 뒤라야 하므로
자동화하지 않는다.

### I6. 승인 이력을 되돌릴 수 있게 한다

메뉴를 잘못 승인하면 지금은 [CMS 메뉴] 에서 보관 처리하는 수밖에 없다.
어떤 제안에서 나온 메뉴인지는 `applied_menu_id` 로 이어져 있으니,
"이 승인 취소" 로 메뉴를 내리고 제안을 검토 대기로 되돌릴 수 있다.

### I7. 운영자 인증

가장 큰 구멍이다. 지금은 주소만 알면 누구나 승인 버튼을 누를 수 있다.
시민에게 나가는 문장을 바꾸는 화면이라 운영 전에 반드시 필요하다.

  "주차장 자리 있나요" 와 "주차 정산 어디서 해요" 가 같은 주제로 들어갔다.
